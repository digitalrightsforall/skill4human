# 智慧逆向工程报告：Architecture Decision Logic (v4.7)

## 适用时机 / Timing & Context
- **典型情景**: 选型技术栈、设计核心模块、或者在面临多个互相矛盾的技术方案时。
- **启动信号**: 当你发现团队正在为“用哪个库”争论不休，且没有明确的评判标准时。
- **[启发式准则]**: 架构决策的价值不在于“正确”，而在于“透明”。

## 核心心法 / Philosophy
- **ADR (Architecture Decision Records)**: 决策是瞬时的，但决策的后果是永恒的。如果不记录当时的“上下文”（为什么这么选）和“权衡”（放弃了什么），未来的维护者将陷入盲目的恐惧。
- **不可逆决策与可逆决策**: 区分那些“昂贵的单向门”决策。
- **[认知增益]**: 获得“历史视野”，让技术演进不再是盲目的重构，而是有根据的进化。

## 落地模型 / System
- **决策三支点**: 
  1. **Context (上下文)**: 我们现在的业务规模、团队能力和时间约束是什么？
  2. **Alternatives (替代方案)**: 我们还考虑了哪些方案？它们为什么落选？
  3. **Consequences (后果)**: 选择这个方案后，未来的哪些扩展会变得困难？
- **[反面模式]**: 盲目追新。因为某个库在 GitHub 上很火就选它，而不考虑团队的维护成本。

## 执行动线 / Workflow
1. **定义问题边界**: 明确我们要解决的核心技术痛点。 -> 2. **草拟方案对撞**: 写下 3 种可能的架构路径。 -> 3. **进行“事后尸检”模拟**: 假设这个方案上线后崩了，最可能的原因是什么？ -> 4. **记录并公示**: 形成一份标准的 ADR 文档。

## 实战技巧 / Tactic
- **成本估算**: “如果选 A，我们需要多招几个这种专家？”
- **[启发式准则]**: 最好的架构是那个能让你以后“最容易纠正错误”的架构。
- **[认知增益]**: 提升“专业公信力”，成为那个在混乱中提供确定性的架构师。
