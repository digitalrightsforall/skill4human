# 智慧逆向工程报告：Elite API Design (v4.7)

## 适用时机 / Timing & Context
- **典型情景**: 设计微服务接口、开源库的公开 API、或系统内部的组件边界时。
- **启动信号**: 当你需要决定“这个参数该怎么传”或者“返回值该长什么样”时。
- **[启发式准则]**: API 是永久性的决策。一旦发布，你就成了它的奴隶。

## 核心心法 / Philosophy
- **契约精神**: API 是一份法律合同。不兼容的改动就是“违约”。
- **最小惊讶原则**: 接口的行为应当完全符合人类的直觉。`save()` 函数不应该暗中修改全局状态。
- **[认知增益]**: 获得“系统构建者”的严谨，设计出能被时间验证的健壮系统。

## 落地模型 / System
- **API 质量四象限**: 
  1. **易发现性 (Discoverability)**: 用户不需要文档也能猜到大部分功能。
  2. **防错性 (Error-Prone Resistance)**: 接口设计应物理上阻止不合法的组合。
  3. **正交性 (Orthogonality)**: 各个 API 之间功能不重叠。
  4. **版本化策略**: 如何优雅地告别旧契约。
- **[反面模式]**: 万能参数。一个参数里塞进 20 个可选标志，让调用者无所适从。

## 执行动线 / Workflow
1. **场景逆向**: 先写调用代码（Consumer-First），再写 API 定义。 -> 2. **契约评审**: 邀请一个完全不知道内部逻辑的人来尝试调用。 -> 3. **边界强化**: 使用类型系统（Type System）来强制执行契约。 -> 4. **文档同步**: 代码即文档，确保示例永远可运行。

## 实战技巧 / Tactic
- **命名即文档**: `fetchActiveUsers()` 比 `get_users(true)` 好 100 倍。
- **[启发式准则]**: 如果你需要一页纸来解释一个 API 的参数含义，那这个 API 设计就是失败的。
- **[认知增益]**: 建立“专业公信力”，让你的接口成为行业标准。
